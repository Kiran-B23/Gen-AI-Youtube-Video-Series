# Research checklist

## Source priority
1. **Official:** product docs, the announcement post, pricing / help / FAQ pages, changelog, the GitHub repo, the paper.
2. **Independent testing:** reputable reviews, benchmarks by third parties, credible creators who actually used it.
3. **Reporting:** established tech press (for context, reactions, competitors).
4. **Community:** forums/social for real pain points and questions (never as the only source of a fact).

Note every source's **publish date**. Prefer the newest for fast-moving tools.

## Fact sheet columns (research.md)
`# | fact | source link | date | label | viewer value (why it matters) | use in`
- **label:** `company claim` / `independent` / `our test` / `community`
- **use in:** reel / explainer / session / cut

## What to collect
- What it is, described by what it **does** (one sentence a beginner understands)
- Who it's for, and the problem it removes
- How it works (the mechanism, plus a candidate **analogy**)
- One **real example or story** (a user anecdote, demo, case study) to use as the running example
- Numbers worth showing (speed, cost, scale), each with a label
- Limitations, risks, costs and gotchas: **always** at least one honest catch
- Alternatives / competitors and how it differs
- The bigger picture (where this is heading)
- Questions viewers will ask (availability, price, safety, "can I use it today?")

## Viewer-value filter (apply to every fact)
Keep a fact only if it changes what the viewer **knows, believes or can do**. Cut by default:
launch venue/date, company HQ, funding minutiae, internal model names, version numbers, award
mentions. Exception: when the fact *is* the story (e.g. "launched yesterday and already…").

## Unverified claims
If a claim can't be confirmed from a primary or independent source, either drop it or say
"reportedly" in the script **and** flag it in the final summary to the user.
